# Ragent 源码拷打 20 问答辩稿

> 口径说明：下面答案按企业内部文档问答场景和当前项目源码实现来回答。每个问题都尽量区分“已经实现的机制”和“线上/规模化时需要补强的点”，面试时不要把改进项说成已经完整落地。

## 1. `/rag/v3/chat` 的完整链路你能手画出来吗？为什么是“记忆 -> 重写 -> 意图 -> 澄清 -> 检索 -> 生成”这个顺序？

可以。主链路是：

```text
RAGChatController
  -> RAGChatServiceImpl
    -> StreamChatPipeline.execute()
      1. loadMemory()
      2. rewriteQuery()
      3. resolveIntents()
      4. handleGuidance()
      5. handleSystemOnly()
      6. retrieve()
      7. handleEmptyRetrieval()
      8. streamRagResponse()
```

这个顺序是为了让每一步给后面的步骤提供更稳定的输入。

`loadMemory()` 放在最前面，是因为企业内部问答里用户经常会说“刚才那个流程”“这个权限怎么申请”，如果不先加载会话历史，后面的 Query Rewrite 没法补全指代和业务上下文。

`rewriteQuery()` 在意图识别前执行，是为了先把口语化、缩写、上下文指代统一成更适合模型判断和检索的表达。例如“这个怎么走审批”要补全成“OA 系统中费用报销审批流程如何提交和流转”。

`resolveIntents()` 在检索前执行，是为了决定应该查哪个知识域、是否调用 MCP 工具、还是走系统指令。意图结果会影响检索路由，比如命中某个业务知识库时优先走意图定向检索。

`handleGuidance()` 在检索前执行，是因为如果意图低置信度或者多个业务域非常接近，直接检索可能会查错库。先澄清可以减少无效召回和错误回答。

`handleSystemOnly()` 在检索前短路，是为了避免类似“清空上下文”“重新开始”这种系统指令还去查知识库，浪费资源并且可能产生错误上下文。

最后才是 `retrieve()` 和 `streamRagResponse()`。检索拿到上下文后，才组装 Prompt 并调用大模型流式生成。

面试里可以补一句：这个链路本质是“先理解用户问题，再决定查哪里，最后带证据回答”。顺序错了会导致后续模块拿到的是不完整或者不稳定的输入。

## 2. 简历里的 `Recall@1 提升 18.8%`、`Top-1 提升 28.5%`、`上下文精准度提升 20.5%` 是怎么测的？数据集规模、baseline、评测口径、是否做 ablation？

我的评测不是只看模型最终回答，而是把 RAG 链路拆成可观测的中间指标。项目里有评测入口，会输出重写后的问题、意图叶子节点、召回文档 ID、召回 chunk ID、召回上下文和耗时，离线脚本再和标注集对齐计算指标。

评测集按企业内部知识场景构建，例如 150 条样本，覆盖制度查询、流程办理、技术文档检索、系统操作指南、权限申请、MCP 工具调用等类型。每条样本标注：

- 用户原始问题
- 期望命中的文档 ID 或 chunk ID
- 期望意图标签
- 标准答案或参考答案
- 难度等级，例如单跳、多跳、跨部门流程、制度边界类

几个指标的口径是：

- `Recall@1`：检索返回的第 1 个结果是否命中标注文档或标注 chunk。
- `Top-1`：一般指 Top-1 召回命中率，或者在意图模块里指 Top-1 意图准确率。面试时要说清楚自己简历上的口径，建议统一成“Top-1 召回命中率”。
- `上下文精准度`：进入 Prompt 的上下文中，有多少比例是真正和标准答案相关的内容。可以按 chunk 级人工标注，也可以借助 RAGAS 的 context precision 计算。

baseline 和 ablation 可以这样设计：

```text
baseline A：原始 query + 全局向量检索
baseline B：术语归一化 + 全局向量检索
ablation C：问题重写 + 全局向量检索
ablation D：问题重写 + 意图定向检索
full：问题重写/拆分 + 意图定向检索 + 全局向量检索 + 去重 + rerank
```

提升值来自同一批评测集上的对比，而不是线上主观感受。面试官如果追问，我会强调：评测时固定模型版本、固定知识库版本、固定 topK、固定随机参数，避免因为知识库变化或模型变化导致指标不可复现。

## 3. 问题重写为什么要先术语归一化再调 LLM？如果 LLM 把用户问题改偏了，怎么检测和回滚？

先做术语归一化，是为了把业务中的别名、缩写、口语说法先统一到知识库里的标准表达，再交给 LLM 改写。这样可以降低 LLM 自由发挥的空间。

例如用户问“OA 单子怎么撤回”，知识库里写的是“OA 审批流程撤回与重新提交操作说明”。如果不先归一化，LLM 可能只做语言润色，不一定能把业务术语改到和文档一致。

当前源码里的流程是：

```text
原始 query
  -> QueryTermMappingService.normalize()
  -> MultiQuestionRewriteService 调 LLM
  -> 解析 JSON 得到 rewrite 和 sub_questions
  -> 失败则 fallback 到 normalizedQuestion
```

也就是说，已经有两层兜底：

- 如果关闭重写，就用归一化后的 query 加规则拆分。
- 如果 LLM 调用失败或 JSON 解析失败，就回退到归一化后的原问题。

但是当前实现对“语义改偏”只做了基础兜底，还没有完整的语义漂移检测。面试时要诚实说：现在主要防调用失败和格式失败，语义漂移可以继续补强。

补强方案：

- 实体约束：系统名称、流程名称、部门、金额、时间、权限范围、制度条件不能被删除或替换。
- 意图一致性：重写前后再做一次轻量意图判断，如果意图差异过大就回滚。
- 相似度阈值：原 query 和 rewrite 做 embedding 相似度，低于阈值判定为改偏。
- 双路检索兜底：同时用原始 query 和 rewrite 检索，合并后 rerank，避免单一路径改偏。
- Prompt 约束：要求 LLM 只补全上下文和规范术语，不允许新增用户没有表达的条件。

## 4. 子问题拆分后，每个子问题独立检索再合并。复杂多跳问题里，子问题之间的依赖关系丢失怎么办？

当前实现更偏“并列子问题拆分”。也就是把复杂问题拆成多个可以并行检索的子问题，然后分别召回上下文再合并。例如：

```text
新员工入职后，邮箱、VPN 和 GitLab 权限分别怎么申请？
```

可以拆成：

```text
新员工邮箱开通流程
VPN 权限申请流程
GitLab 代码仓库权限申请流程
```

这种场景并行检索是有效的，因为子问题之间依赖不强。

但对于多跳依赖问题，例如“如果我这次出差跨了两个城市，还包含客户招待，差旅报销和招待费报销需要分别走什么流程，附件怎么准备”，子问题之间存在顺序依赖：先识别费用类型，再查差旅制度和招待费制度，再判断审批路径和附件要求。如果完全独立检索，确实可能丢失依赖关系。

解决思路有三层：

- 拆分时给子问题带上共享上下文，例如员工身份、部门、流程类型、金额、时间、系统名称，不让每个子问题变成孤立问题。
- 对子问题标记类型，例如 `parallel` 和 `dependent`。并列对比类可以并发，规则推导类要按步骤执行。
- 在生成阶段把所有子问题、召回证据和原问题一起放入 Prompt，让模型基于整体问题做最终归纳，而不是分别回答后简单拼接。

如果进一步工程化，可以把子问题拆分结果从简单 List 升级成 DAG：

```text
识别业务场景 -> 查询制度条款 -> 查询系统操作流程 -> 汇总审批路径和材料要求
```

当前项目的并行拆分适合提升召回覆盖率，但对强依赖多跳推理，需要引入任务编排或者工具调用链路来补强。

## 5. 术语归一化的规则冲突怎么处理？比如多个 `source_term` 命中、模糊匹配误伤、业务缩写一词多义时谁优先？

当前术语归一化的规则主要靠优先级和最长匹配解决冲突。规则从缓存或数据库加载后，会按 `priority` 降序排序，同优先级下按 `source_term` 长度降序排序。这样可以优先处理更重要、更具体的规则。

例如同时有：

```text
OA -> OA 审批系统
OA 报销 -> OA 费用报销流程
```

在相同优先级下，会先匹配“OA 报销”，避免先把“OA”替换掉导致长词失效。

如果多个规则都命中，当前实现偏确定性替换，而不是让 LLM 判断。好处是可控、可解释；问题是对一词多义和模糊匹配不够强。

面试可以这样回答风险：

- 对精确别名、系统名称、流程名称、常见缩写，用规则归一化。
- 对一词多义缩写，不直接全局替换，而是加业务域限制，例如财务域、IT 运维域、人事制度域。
- 对容易误伤的词，不做 substring 模糊替换，改用词边界、正则或意图上下文约束。
- 每条规则保留优先级、启停状态、命中日志，方便灰度和回滚。

如果面试官追问“怎么解决业务缩写一词多义”，可以说：不能只靠静态替换，应该先做候选规则召回，再结合意图或上下文消歧。例如“OA”可能指 OA 审批系统，也可能指某个办公自动化项目代号；“VPN”在权限申请场景是远程访问权限，在网络故障场景可能是排障对象，必须带上业务域。

## 6. 意图识别树现在是把叶子节点拼进 Prompt 让 LLM 打分。意图节点从几十个涨到几千个时，Token、延迟、准确率怎么解决？

当前实现适合中小规模意图树：把叶子节点序列化进 Prompt，让 LLM 对用户问题和候选意图打分，然后取超过阈值的 Top 意图。几十个到一两百个意图时，这种方式简单、准确、可解释。

但涨到几千个意图时会有明显问题：

- Prompt 太长，Token 成本高。
- LLM 分类延迟高。
- 候选太多会稀释注意力，准确率下降。
- 意图树频繁变化时 Prompt 构造成本也会上升。

解决方案是两阶段或多阶段分类。

第一阶段做候选召回，不让 LLM 看全部意图：

```text
用户 query
  -> embedding / BM25 / 关键词规则召回 TopN 候选意图
  -> 只把 TopN 意图交给 LLM 精排打分
```

第二阶段再让 LLM 精排：

```text
候选意图 Top20
  -> LLM 结合描述、示例、边界进行打分
  -> 输出 Top3 意图和置信度
```

也可以按树分层做：

```text
先判断一级意图
  -> 再在命中的一级意图下面判断二级/叶子意图
```

这样 Token 从“全量叶子节点”变成“候选节点”，延迟和成本都可控。线上还可以缓存意图树摘要、缓存高频 query 的分类结果，并给强规则意图加前置判断。

## 7. LLM 输出的 intent score 不是严格校准概率，你为什么敢用 `0.4`、`0.6`、`0.8` 这些阈值？怎么调参？

我不会把 LLM 输出的 score 当成严格概率，而是当成排序和置信度信号。阈值不是理论上拍脑袋来的，而是通过离线评测集调出来的工程阈值。

当前几个阈值含义不同：

- `0.4` 左右用于判断一个意图是否值得进入意图定向检索，偏召回。
- `0.6` 左右用于判断意图是否足够可靠，如果低于这个值就补充全局向量检索，防止查错库。
- `0.8` 左右用于判断单意图是否足够强，如果只有一个中等置信意图，也会补充全局检索。

调参方法是：

```text
固定评测集
  -> 跑不同阈值组合
  -> 观察意图准确率、召回率、澄清率、误澄清率、平均延迟
  -> 选择业务可接受的平衡点
```

阈值调优不只看准确率，还要看误伤成本。如果阈值太低，系统会过度相信错误意图，导致查错知识库；如果阈值太高，会频繁走全局检索或澄清，增加延迟和用户轮次。

所以这些阈值本质是“风险控制开关”：低置信时多查一路或反问，高置信时走更精准的意图定向检索。

## 8. 低置信度澄清反问的触发条件是什么？误触发会增加用户轮次，不触发会检索错库，你怎么权衡？

当前澄清不是只看一个低分就触发，而是看候选意图之间是否真的存在歧义。

大致逻辑是：

- 只在候选意图数量适合判断歧义时触发。
- 过滤掉分数太低的意图。
- 按业务系统或类目聚合，取每组最高分。
- 如果只有一个明显领先的候选，就不澄清。
- 如果 Top1 和 Top2 分数接近，说明用户表达可能跨域或不明确，再触发澄清。
- 如果用户问题里已经显式出现业务域别名，则跳过澄清。

权衡点是：澄清的目标不是追求绝对正确，而是避免“高代价错误”。例如财务报销制度、权限开通、合同审批、数据安全规范这类问题，查错库的风险比多问一句更高；而普通制度定义或系统入口查询，可以更偏向直接检索。

可以用两个指标调这个模块：

- 误澄清率：本来可以直接回答却触发澄清的比例。
- 错库拦截率：如果不澄清会查错库，而澄清成功避免错误的比例。

面试时可以说：我会把澄清设计成“低频但高价值”，不是所有低置信都反问，而是在候选意图接近、业务域冲突、问题缺少关键槽位时才反问。

## 9. `SYSTEM`、`KB`、`MCP` 混合意图同时命中时，谁优先？如果系统指令和知识库问答冲突怎么办？

项目里意图类型主要分成三类：

- `SYSTEM`：系统级指令，例如清空上下文、重新开始。
- `KB`：知识库问答。
- `MCP`：需要调用外部工具或业务系统。

当前实现里，如果识别结果是纯 `SYSTEM`，会在检索前短路，不走知识库检索。例如用户明确说“清空上下文”，就不需要召回文档。

如果是 `KB` 和 `MCP` 混合意图，则会继续走后续链路：KB 负责检索知识上下文，MCP 负责补充工具调用上下文，最后一起进入 Prompt。

如果 `SYSTEM` 和 `KB/MCP` 混合命中，原则上系统指令应该优先于知识库内容。原因是系统指令影响对话状态或安全边界，不能被知识库内容覆盖。例如用户说“忽略前面的上下文，然后告诉我报销制度”，其中“忽略上下文”是会话控制，“报销制度”是知识问答，需要明确拆开处理。

面试可以补充当前实现边界：源码里对纯系统指令有短路处理，但对复杂混合冲突还可以继续增强，例如增加优先级仲裁器：

```text
安全/权限/系统控制 > MCP 工具执行约束 > KB 知识回答 > 普通生成
```

同时在 Prompt 层也要强调：系统规则和工具返回结果优先级高于普通知识库片段。

## 10. 多路检索里，意图定向检索和全局向量检索分别解决什么问题？什么情况下只走一路，什么情况下双路都走？

意图定向检索解决的是“精准查库”问题。用户意图比较明确时，只在相关知识库或相关 collection 中检索，可以减少无关 chunk 干扰，提高上下文精准度。

全局向量检索解决的是“兜底召回”问题。当意图识别不够确定，或者用户问题跨多个业务域时，全局检索可以避免因为意图识别错误导致完全查不到正确文档。

可以这样理解：

```text
意图定向检索：高精度，适合意图明确的问题
全局向量检索：高覆盖，适合意图不确定或跨域问题
```

当前项目的策略是按置信度决定：

- 意图定向检索开启，并且存在分数超过阈值的 KB 意图时，走意图定向检索。
- 如果意图定向关闭、没有可靠意图、最高意图分数低于置信阈值，走全局向量检索。
- 如果只有一个中等置信意图，也会补充全局向量检索，避免单意图误判。
- 高置信且明确的单域问题，可以主要依赖意图定向检索。

双路都走的代价是延迟和候选变多，所以后面必须有去重、rerank 和 TopK 控制。否则全局检索召回的噪声会污染 Prompt。

## 11. `CompletableFuture.join()` 等所有检索任务完成，如果某个 collection 或 embedding 调用卡住，会不会拖垮整次请求？有没有超时、隔离、降级？

这个问题很关键。当前多路检索和多 collection 检索确实用了 `CompletableFuture` 并行化，异常会被捕获并降级为空结果，但如果底层调用一直卡住，而没有明确超时，就可能拖慢整个请求。

当前已有的保护主要是：

- 不同检索任务通过线程池并发执行，避免串行阻塞。
- 单个任务异常时返回空集合，不让异常直接打爆整条链路。
- 多通道结果会合并，某一路失败时理论上可以依赖其他检索通道兜底。

但这还不够。真正线上化要加四类控制：

- 连接和读超时：数据库、embedding 服务、rerank 服务、LLM HTTP 客户端都要设置超时。
- Future 级超时：对每个检索任务加 `orTimeout` 或 `completeOnTimeout(empty)`。
- 资源隔离：不同通道、不同外部模型调用使用独立线程池或 bulkhead，避免一个慢依赖占满全部线程。
- 降级策略：某个 collection 超时就跳过；embedding 服务不可用时返回澄清/稍后重试；rerank 超时就用原始相似度排序。

面试回答可以说：现在代码有异常隔离，但超时隔离还需要进一步补强。并行化只解决平均延迟，不能自动解决尾延迟，尾延迟必须靠 deadline 和降级。

## 12. Rerank 是唯一做 TopK 截断的地方。如果 `rag.rerank.enabled=false`，大量 chunk 会直接进 Prompt，你怎么控制 Token 成本和上下文污染？

这是当前设计里需要特别注意的点。项目后处理链路是先去重，再 rerank。`RerankPostProcessor` 不只是重排，也承担了 TopK 截断。如果关闭 rerank，去重后的所有 chunk 可能继续进入 Prompt，带来两个风险：

- Token 成本不可控。
- 无关上下文增多，影响模型回答质量。

面试时不能硬说没问题，应该承认这是一个配置风险。解决方案是把“TopK 截断”和“rerank”解耦。

更合理的后处理链路是：

```text
merge
  -> dedup
  -> optional rerank
  -> mandatory topK cutoff
  -> token budget filter
```

也就是说，即使 `rag.rerank.enabled=false`，也应该有一个强制的 `TopKCutoffPostProcessor` 或 Prompt 组装前的 token budget guard。

另外还可以在检索入口控制：

- 每个 channel 限制候选数。
- 每个 collection 限制 topN。
- 同一文档最多保留 N 个 chunk。
- Prompt 组装时按 token 预算截断。

一句话总结：rerank 可以关闭，但 TopK 和 token budget 不能关闭。

## 13. 去重逻辑用 chunk id 或文本 hash。不同 chunk 内容高度相似但 id 不同怎么办？同一文档相邻 chunk 重复召回怎么处理？

当前去重是精确去重：优先用 chunk id，没有 id 时用文本 hash。它能解决同一个 chunk 被不同通道重复召回的问题，比如意图定向和全局向量都召回了同一条 chunk。

但它解决不了近重复问题：

- 两个 chunk id 不同，但内容高度相似。
- 同一文档相邻 chunk 因为 overlap 导致重复。
- 同一段政策在不同文档中复制粘贴。

这类问题需要“语义去重”或“文档级合并”。

可选方案：

- SimHash / MinHash：对文本近重复做快速判断。
- embedding 相似度：两个 chunk 相似度超过阈值时只保留分数更高的。
- 相邻 chunk 合并：同一 doc 下连续 chunk 被召回时，合并成一个更完整的上下文窗口。
- MMR 多样性排序：在相关性之外加入多样性，避免 TopK 都来自同一文档同一段。
- doc-level quota：同一文档最多保留 N 个 chunk，防止一个文档刷屏。

面试时可以说：当前实现先做了确定性去重，保证工程简单稳定；后续如果知识库中重复内容多，会补语义去重和相邻 chunk 合并。

## 14. pgvector 查询里用 `metadata->>'collection_name'` 过滤再按 HNSW 排序。你看过执行计划吗？数据量大时索引会怎么走？

当前 pgvector 查询的核心形态是：

```sql
SELECT id, content, 1 - (embedding <=> ?::vector) AS score
FROM t_knowledge_vector
WHERE metadata->>'collection_name' = ?
ORDER BY embedding <=> ?::vector
LIMIT ?
```

这里有两个点要关注：

- 向量排序希望走 pgvector 的 HNSW 索引。
- `metadata->>'collection_name'` 是 JSONB 表达式过滤。

如果数据量小，这样写问题不大。但数据量大时要看 `EXPLAIN ANALYZE`。风险是数据库可能先走向量索引再做 metadata 过滤，也可能因为表达式过滤选择不理想的计划，导致扫描候选过多。

优化方向：

- 把 `collection_name` 从 JSONB metadata 中提升为普通列，单独建 BTree 索引。
- 对 JSONB 表达式建 expression index，例如 `(metadata->>'collection_name')`。
- 对不同 collection 拆分表或分区，减少单次向量搜索空间。
- 对高频 collection 建 partial vector index。
- 定期用 `EXPLAIN ANALYZE` 验证不同数据量下的执行计划和耗时。

面试可以诚实说：源码层面能看到查询方式，但真正的索引效果必须结合数据量、索引定义和执行计划看。RAG 系统不能只写 SQL，要验证向量索引和过滤条件是否按预期工作。

## 15. embedding 入库和查询时的归一化是否一致？如果换 embedding 模型或维度从 1536 变了，历史向量怎么迁移？

embedding 一致性包括三件事：

- 入库和查询使用同一个 embedding 模型。
- 向量维度一致。
- 相似度计算方式和归一化策略一致。

当前项目配置里 embedding 模型和维度是可配置的，知识库也会记录 embedding model。项目在知识库已有文档时限制直接修改 embedding model，这个设计是对的，因为不同模型生成的向量不在同一个向量空间，不能混查。

如果要从一个 1536 维模型切到另一个模型，不能直接改配置后继续写入。正确迁移流程是：

```text
1. 创建新 embedding 模型配置和新向量空间
2. 对历史原文档重新切块
3. 用新模型重新生成 embedding
4. 写入新 collection 或新表
5. 灰度让查询同时支持新旧向量库
6. 验证召回指标后切流
7. 清理旧向量
```

至于归一化，要保证入库和查询一致。如果使用 cosine distance，pgvector 可以直接算 cosine，但工程上最好在 embedding 服务或向量存储层统一处理，避免“查询向量归一化、入库向量未归一化”这种隐性不一致。

面试可以补一句：embedding 模型升级不是热更新配置，而是一次完整的索引重建和评测回归。

## 16. 会话记忆用滑动窗口 + 异步摘要。摘要生成失败、延迟、或者摘要把关键信息压丢了，对下一轮问答有什么影响？

会话记忆分两部分：

- 短期记忆：最近 N 轮原始消息，保证细节不丢。
- 长期摘要：超过阈值的历史对话压缩成 summary，控制 token 成本。

当前摘要是异步触发的，所以摘要生成失败或延迟时，不会阻塞当前回答。下一轮对话至少还能加载最近窗口内的消息。如果摘要失败，就继续使用旧摘要或空摘要。

风险在于：

- 摘要延迟：下一轮可能还看不到刚压缩出的历史信息。
- 摘要失败：长历史只能依赖滑动窗口，窗口外信息可能缺失。
- 摘要压丢关键事实：用户所属部门、角色权限、正在办理的流程、之前确认过的系统或制度范围可能丢失。

缓解方案：

- 保留原始消息，不用摘要替代原文，只是摘要作为检索/Prompt 的压缩视图。
- 摘要 Prompt 要明确保留实体、时间、员工身份、业务上下文、已确认流程、未完成任务。
- 采用结构化摘要，例如员工角色、已确认信息、待办事项、关键约束分字段保存。
- 下一轮回答时遵循“最近原文优先于历史摘要”，避免旧摘要覆盖新对话。
- 摘要失败要可重试，并记录失败原因。

面试可以说：滑动窗口解决短期准确性，摘要解决长期成本；两者不是互相替代，而是互补。

## 17. 摘要压缩为什么在 assistant 消息 append 后触发？并发同一个会话多轮请求时，Redisson 锁能保证不会重复摘要或漏摘要吗？

摘要在 assistant 消息 append 后触发，是因为一轮完整对话应该包括用户问题和助手回答。如果只在 user 消息后触发，摘要里可能只有问题没有答案，长期记忆是不完整的。

当前流程大致是：

```text
append user message
生成 assistant response
append assistant message
如果超过阈值，触发异步摘要压缩
```

并发控制上，项目使用 Redisson 锁按用户和会话维度加锁，避免同一个 conversation 同时有多个摘要任务并发执行。摘要时还会根据 `lastMessageId` 或 cutoff 位置判断哪些消息已经被摘要过，避免重复压缩。

但锁只能解决“同一时刻只有一个摘要任务执行”，不能天然保证所有极端并发场景都完美。例如：

- 两个请求几乎同时 append 消息，摘要任务看到的消息边界不同。
- 摘要任务执行较慢，期间又有新消息进入。
- 异步任务失败后，需要下一轮重新触发。

所以正确设计是：

- 用分布式锁保证同一会话摘要串行。
- 用 `lastMessageId` 保证幂等，只摘要未处理区间。
- 保留最近窗口，不把正在活跃的消息提前压缩。
- 摘要更新使用事务或乐观锁，避免覆盖更新。

面试回答可以说：Redisson 锁降低重复摘要风险，`lastMessageId` 控制摘要边界，滑动窗口兜底漏摘要影响。严格来说，摘要模块要按“最终一致”设计，而不是强一致。

## 18. 分布式排队限流怎么证明“公平”？ZSET 排队、Lua claim、permit 获取之间有竞态时，如何避免插队、permit 泄漏和队列僵尸项？

项目里的公平限流核心是 Redis ZSET + Lua 原子脚本 + Redisson permit。

请求进入时会拿到一个递增序号，并写入 ZSET。ZSET 的 score 表示排队顺序，所以天然可以按先进先出处理。Lua claim 脚本在 Redis 内部原子执行，检查队头可用名额，只允许排在前面的请求被 claim。

公平性的含义不是绝对实时公平，而是在 Redis 顺序号下做到“活跃请求按入队顺序获取资格”。

几个竞态点的处理思路：

- 插队：claim 时只看 ZSET 头部窗口，后来的请求 score 更大，不能越过前面的 live entry。
- permit 泄漏：拿到 permit 后用 try/finally 释放；如果业务异常也释放。
- claim 成功但 permit 获取失败：把 entry 按原 score 放回队列，保留原位置。
- 队列僵尸项：每个排队 entry 有 marker TTL，Lua 扫描时发现 marker 不存在就清理 ZSET。
- 超时取消：请求超时后 CAS 修改 ticket 状态，并从队列移除。
- 多实例并发：claim 动作在 Redis Lua 内原子执行，不依赖本地 JVM 锁。

面试可以补一句：公平限流最怕“检查队头”和“扣减资源”不是原子操作。项目里把队列 claim 放进 Lua，permit 生命周期放进 finally，僵尸项靠 TTL 清理，这三个点共同保证不会长期插队、泄漏或卡死。

## 19. 模型路由熔断状态存在本地内存。多实例部署时，一个实例熔断了另一个实例不知道，这算不算问题？怎么改成集群级健康状态？

这算一个需要看部署规模的问题。

当前模型健康状态存在本地内存，优点是简单、快速、没有外部依赖。单实例或者小规模部署时足够用：某个模型连续失败达到阈值，本实例会把它打开熔断，后续请求优先走其他候选模型。

但多实例部署时，本地熔断有局限：

- A 实例发现模型失败并熔断，B 实例不知道，仍然可能继续打到失败模型。
- 每个实例看到的错误样本不同，熔断状态不一致。
- 模型供应商区域性故障时，集群整体恢复会比较慢。

改成集群级健康状态可以有几种方案：

- Redis 存储模型健康状态和失败计数，所有实例共享。
- 使用滑动窗口统计失败率，而不是简单连续失败次数。
- 接入 Prometheus 指标，通过控制面动态下发模型权重。
- 在网关或模型代理层做统一熔断，业务实例只感知可用模型列表。
- 本地熔断 + 集群熔断结合：本地保护尾延迟，集群状态保护全局故障。

面试时可以说：本地熔断不是错，它适合保护单实例线程和延迟；但如果要多实例一致避障，需要把健康状态上移到 Redis、配置中心或模型代理层。

## 20. 全链路追踪现在主要记录耗时和状态，不记录中间 chunk、rewrite、intent 细节。线上回答错了，你怎么定位是重写错、意图错、召回错、rerank 错，还是模型生成错？

当前链路追踪能记录每个节点的耗时、状态和异常，比如重写、意图、检索、生成哪个阶段慢了或失败了。但如果只记录耗时，不记录关键中间结果，定位“回答错了”确实不够。

排查思路是把错误拆成几个阶段：

```text
原问题是否被改写错？
  -> 看 rewrite 和 sub_questions
意图是否识别错？
  -> 看 Top intents、score、是否触发澄清
召回是否错？
  -> 看每个 channel 召回的 doc/chunk id 和 score
rerank 是否错？
  -> 看 rerank 前后排序变化
Prompt 是否污染？
  -> 看进入 Prompt 的最终上下文
生成是否幻觉？
  -> 看上下文里是否包含答案证据
```

当前可以结合评测接口和日志做离线复现，但线上最好增强 trace 的 `extraData`。注意不能无脑记录完整用户问题和完整文档内容，因为可能有隐私和数据安全风险。

推荐记录安全元数据：

- rewrite 后问题
- sub question 数量和内容摘要
- Top intent id、name、score
- 每个检索通道返回的 chunk id、doc id、score
- dedup 删除了哪些重复 id
- rerank 前后 TopK id 列表
- 最终进入 Prompt 的 chunk id
- 模型名称、路由结果、是否发生降级

这样线上回答错了，可以快速判断：

- rewrite 后语义变了：重写问题。
- intent Top1 错了：意图问题。
- 正确文档没有召回：召回问题。
- 正确文档召回了但 rerank 排掉了：rerank 问题。
- 正确上下文进入 Prompt 但回答错：生成或 Prompt 约束问题。

一句话总结：RAG 排障不能只看最终答案，要把“重写、意图、召回、重排、生成”每一层的输入输出都留下可审计的轻量证据。

## 面试收尾总结

这个项目的核心不是简单把文档塞进向量库，而是把 RAG 链路拆成了可控制、可评测、可降级的多个阶段：

```text
会话记忆
  -> 问题重写和拆分
  -> 意图识别和澄清
  -> 多路并行检索
  -> 去重和 rerank
  -> 流式生成
  -> 限流、熔断、追踪保障
```

面试时要注意两种表达：

- 已经落地的：按源码讲清楚类、链路、阈值、降级逻辑。
- 可以优化的：主动承认边界，并给出工程上可落地的改进方案。

这样回答会比单纯背技术名词更稳，因为面试官追问时，你能把设计选择、风险和后续演进讲完整。
